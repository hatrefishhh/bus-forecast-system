## 1. 設計規則

### 版面

- 這是**操作型工具，不是形象首頁**。
  - 打開就是可操作的畫面：篩選列、圖表、表格。
  - 不要有 hero 區塊、大 logo、大圖、宣傳標語、「開始使用」按鈕。
  - 不要有一整排巨大數字的統計卡片。
- 新頁面沿用現有頁面的骨架：上方篩選列、主圖、明細表、匯出。
- 桌面 1440px 和手機 390px 都要能操作。手機不能有整頁橫向捲動，表格在容器內捲動。

### 文字

- **能短就短。**
  - 頁面標題下最多一行副標，沒有必要就不放。
  - 按鈕和欄位標籤用名詞或動詞片語，不寫句子。
- **畫面上不放風險、限制、免責的說明段落。** 這類補充全部改成 `InfoTip`（見第 2 節）。
  - 做法：在術語或數字旁放一個小圖示，或把術語加上虛線底線。
  - 游標移上去、鍵盤 focus、手機點一下時，才浮出說明。
- 資料正確性的規則照舊：無紀錄不補 0、留缺口、不放假數字。但**用視覺表達，不用句子解釋**。
  - 例如：缺口加琥珀細帶，圖例寫「無紀錄」三個字。
  - 細節放進 InfoTip。
- 空狀態和錯誤狀態：一行短句加一個動作按鈕。

## 2. 共用元件：InfoTip（先做）

`frontend/src/components/InfoTip.tsx`

- 觸發元素是 `<button type="button">`，用 `aria-describedby` 連到說明。
  - 滑鼠移入、鍵盤 focus 時顯示；Esc 和失焦時關閉。
  - 觸控裝置點一下開、點外面關。
  - 不能只做 hover，手機會用不了。
- 兩種外觀：
  - 小圖示：ⓘ 或 tokens 允許的等效符號。
  - 包住一段文字並加虛線底線。
- 浮層位置自動避開視窗邊緣。z-index 用 `--z-tooltip`。
- 寬度上限約 32ch，內文用 `--text-sm`。
- 動畫只用 `--dur-micro`，並尊重 `prefers-reduced-motion`。

## 3. 新頁面：班次情境（`/scenario`，導覽列名稱「班次情境」）

### 目的

比較兩種「每小時發車班次」配置和歷史需求的對照，回答「班次該往哪些時段挪」。

這是規則計算，不需要機器學習。

### 輸入

| 輸入 | 說明 |
|---|---|
| 需求期間 | 沿用現有日期篩選；預設 2025 全年 |
| 日別 | 平日（週一至週五）／週末（週六、週日）／全部 |
| 需求來源 | 預設「歷史平均」。第 4 節的預測檔存在時，可切換成「預測」 |
| 方案 A（AS-IS） | 每小時班次數，範圍 5 到 23 時。每格是 0 以上的整數 |
| 方案 B（TO-BE） | 同上 |
| 每班容量 | 一個整數（人／班），兩方案共用 |
| 路線單程里程 | 公里，可留空 |
| 高載門檻、低載門檻 | 預設 1.0 和 0.3，可調整 |

基準時刻表的來源：

- 如果 `data/prepared/timetable_baseline.csv` 存在，方案 A 預設帶入它。
  - 欄位：`route,day_type,hour,departures,source,updated_at`
  - `day_type` 是 `weekday` 或 `weekend`
- **不存在時，方案 A 和方案 B 都是空白**。畫面顯示一行「尚未設定基準班次」，旁邊放「手動輸入」和「匯入 CSV」兩個按鈕。
- **不要內建任何假的預設班表。**
- 輸入值要寫進網址 query，例如 `a=0,0,2,3,...`、`b=...`、`cap=...`、`km=...`、`day=weekday`。這樣網址可以分享，重新整理也能還原。

### 計算（放後端，前端只顯示結果）

設 h 為小時，D 為選定期間內、選定日別中「有紀錄的日數」。

| 指標 | 定義 |
|---|---|
| 平均需求 `d_h` | 該小時旅次總和 ÷ D。若該小時在期間內從未出現，記為 `null`（圖上留缺口，不當 0） |
| 供給座位 `s_h` | 班次數 × 每班容量 |
| 負載比 `r_h` | `d_h / s_h`。`s_h = 0` 且 `d_h > 0` 時記為「無班次但有需求」，另外標記 |
| 高載時段數 | 符合 `r_h ≥ 高載門檻` 的小時數 |
| 低載時段數 | 符合 `r_h ≤ 低載門檻` 的小時數 |
| 超出座位人次 | `Σ max(0, d_h − s_h)` |
| 總班次 | `Σ 班次數` |
| 車公里 | 總班次 × 單程里程。里程留空時顯示「—」 |

注意事項（全部放 InfoTip，不寫在畫面上）：

- 上車人次不等於車上人數，同一個座位沿線可以載不只一人，所以負載比只是粗略指標。
- 「超出座位人次」不是實際沒搭上車的人數。
- 方向尚未分類，這裡是兩方向合計。

D 的定義有一個待確認的地方：某小時在「有紀錄的日子」裡沒出現，目前當作 0 旅次計入平均。開工前把這點列在 PR 說明裡，請我確認。

### 一鍵建議（「依需求分配」按鈕）

- 讓方案 B 的總班次和方案 A 相同。
- 在方案 A 有發車的時段裡，依 `d_h` 的比例分配班次。
  - 用最大餘數法取整數。
  - 每個原本有發車的時段至少保留 1 班。
- 分配結果寫進方案 B，使用者之後仍可手動修改。
- 這是確定性演算法，必須寫單元測試。

### API

- `GET /api/scenario/demand?start&end&day_type&source=history|forecast`：回傳每小時的 `d_h`、D、`warnings`。
- `POST /api/scenario/compare`：
  - body 是兩方案、容量、里程、門檻和需求參數。
  - 回傳逐小時明細和兩方案的指標。
- `POST /api/scenario/suggest`：回傳方案 B 的班次陣列。
- 錯誤格式沿用現有的 `{"detail": {"code","message","field"}}`。
  - 班次數為負數、容量 ≤ 0、陣列長度不對，都回 422。
- `/api/meta` 的 `features.scenario` 改為 `true`。

### 畫面

1. **上方**：篩選列（期間、日別、需求來源），旁邊一列方案參數（容量、里程、門檻）。
2. **主圖**：
   - 橫軸是小時。
   - 需求用線表示。
   - 方案 A、方案 B 的供給座位用並排長條表示。
   - 高載時段用 tokens 允許的強調方式標出。
3. **方案輸入**：一張兩列（A、B）× 19 欄（5 到 23 時）的可編輯數字格。
   - 可以用鍵盤移動。
   - 手機上改成直式列表。
4. **指標對照**：一張小表，列出 A、B 和差異。不要做成大卡片。
5. **匯出**：輸出逐小時對照 CSV，格式沿用現有匯出規則（UTF-8 BOM）。

## 4. 新頁面：需求預測外殼（`/forecast`，導覽列名稱「需求預測」）

模型由另一組人做，網站只負責呈現。**沒有預測檔時，不顯示任何數字。**

### 資料契約

檔案是 `data/prepared/forecast.csv`：

| 欄位 | 型別 | 說明 |
|---|---|---|
| `date` | YYYY-MM-DD | |
| `hour` | 0–23 | |
| `route` | 字串 | 目前只有 `6670D` |
| `direction` | 字串 | 目前只有 `all` |
| `predicted` | 數字 ≥ 0 | 預測旅次 |
| `lower`、`upper` | 數字，可留空 | 區間 |
| `split` | `train`／`valid`／`test`／`future` | |
| `model_version` | 字串 | |
| `generated_at` | ISO 時間 | |

另外寫一份 `docs/forecast_contract.md` 給模型組。內容是上表，加一個三列的範例。

### 行為

- **檔案不存在**：
  - 頁面只顯示「尚無預測結果」和一行契約文件連結。
  - `features.forecast` 為 `false`。
- **檔案存在時**，提供：
  - 預測值和實際值的對照圖，可選日期。實際值取自 `hourly_all_directions.csv`。
  - 在 `valid` 和 `test` 上計算誤差指標，用一張小表呈現：
    - **MAE** = mean(|y − ŷ|)
    - **WAPE** = Σ|y − ŷ| ÷ Σy
    - **尖峰低估率** = 在實際值 ≥ 期間 P90 的時段中，Σmax(0, y − ŷ) ÷ Σy
      - 這個定義要在 PR 說明裡請我和模型組確認。
- 檔案格式錯誤時回 503，並說明是哪一欄錯。不要當成空資料。
- 資料版本（`versioning.py`）要把 `forecast.csv` 納入，但把它當選用檔，缺少時不影響其他頁面。
